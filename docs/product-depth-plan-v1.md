**สถานะ:** พร้อมลงมือ
**วันที่:** 8 กันยายน 2026
**ต่อจาก:** [product-ux-brief-v1.md](product-ux-brief-v1.md) และ [ui-implementation-status.md](ui-implementation-status.md)

## ที่มา

หน้าจอ prototype ครบตามที่กำหนดไว้แล้ว แต่ความครบนั้นวัดที่ "เส้นทางใช้งาน"
ไม่ได้วัดที่ "เหตุผลที่ผู้ใช้จะกลับมา" วงจรปัจจุบันสั้นเกินไป

```
เลือกคอนเทนต์ → ปักสินค้า → ตั้งเวลา → ออก
```

วงจรที่ต้องการ

```
หาโอกาส → สร้าง → ตรวจคุณภาพ → วางแผน → ติดตาม → นำงานเก่ากลับมาใช้ใหม่
```

เอกสารนี้กำหนดกติกาขอบเขต งานฐานที่ต้องทำก่อน และลำดับฟีเจอร์
ทุกฟีเจอร์ทำ UI และ local/mock ให้ใช้งานได้ครบก่อน แล้วค่อยต่อ backend

**ข้อจำกัดที่ตกลงไว้แล้ว:** ไม่เพิ่มแท็บหลัก และไม่ขยายไปแพลตฟอร์มอื่นในตอนนี้

## 1. กติกาขอบเขต — ใช้เช็คทุกไอเดียใหม่

ส่วนนี้สำคัญที่สุดในเอกสาร ใช้ตอบคำถาม "ฟีเจอร์นี้หลุดจุดประสงค์หลักไหม"
ก่อนเริ่มเขียนโค้ดทุกครั้ง

### แบบทดสอบข้อเดียว

> **ฟีเจอร์นี้ทำให้คอนเทนต์ที่มีอยู่แล้ว ไปถึง TikTok พร้อมตะกร้า
> ได้ดีขึ้นหรือบ่อยขึ้นไหม**

| คำตอบ | คำตัดสิน |
|---|---|
| ใช่ | อยู่ในแกน ทำได้เลย |
| ไม่ แต่ช่วยตัดสินใจว่าจะ relay อะไรต่อ | อยู่ขอบ ทำได้ **แต่ต้องอาศัยอยู่ในหน้าที่มีอยู่แล้ว ห้ามมีที่อยู่ของตัวเอง** |
| ไม่ แต่ช่วย *สร้าง* คอนเทนต์ | **หลุด** — นั่นเป็นงานของเครื่องมือ AI ต้นทาง |

### สัญญาณเตือนว่าหลุดแล้ว

เจอข้อไหนให้หยุดและทบทวน

- มีแท็บหลักที่ 6
- มีหน้าที่เข้าไปแล้ว **ไม่มีปุ่มพากลับไปสร้างหรือจัดการงาน**
- ตัวเลขใด ๆ ที่แสดงผล กดแล้วไม่พาไปทำอะไรต่อ
- เริ่มพูดถึง Facebook / Instagram / YouTube
- หน้า AI Create ในแอป เด่นกว่า AI Content Inbox
- เทมเพลตหรือ AI ในแอปเริ่มเก็บ/สร้าง **สคริปต์ hook หรือ storyboard**

### เส้นแบ่ง metadata กับตัวคอนเทนต์

RelayContent เป็นเจ้าของฝั่งซ้าย เครื่องมือ AI ต้นทางเป็นเจ้าของฝั่งขวา
ห้ามข้ามเส้นนี้

| RelayContent เก็บ/แก้ได้ | เป็นของเครื่องมือต้นทาง |
|---|---|
| แพตเทิร์น caption | สคริปต์ บทพูด |
| ชุดแฮชแท็ก | Hook ประโยคเปิด |
| ตำแหน่งปักตะกร้า และ CTA | storyboard ช็อตลิสต์ |
| ความยาวเป้าหมาย | ไอเดียคอนเทนต์ |
| เวลาโพสต์ สินค้าที่ผูก | ตัวไฟล์วิดีโอ |

## 2. สิ่งที่ต้องแก้ใน brief ก่อนเริ่มฟีเจอร์เรื่องรายได้

ประโยคแกนใน brief ปัจจุบันจบที่คำว่า "เผยแพร่" ไม่มีคำว่ารายได้หรือผลลัพธ์
การเพิ่มเรื่องรายได้จึงเป็นการ **ขยายขอบเขตจริง** ต้องแก้ brief ก่อน
ไม่ใช่ทำแล้วหาเหตุผลทีหลัง

**เหตุผลที่ควรขยาย:** คำว่า Affiliate ในกลุ่มผู้ใช้เป้าหมายแปลว่าคอมมิชชัน
ถ้าตัดเรื่องเงินออก สิ่งที่เหลือคือตัวตั้งเวลาโพสต์ TikTok ที่ปักตะกร้าได้
ซึ่งไม่ใช่เครื่องมือของ affiliate

**ประโยคแกนที่เสนอ**

> รับคอนเทนต์ เลือกสินค้า ตรวจความพร้อม ตั้งเวลา Relay ไปพร้อมตะกร้า
> **แล้วบอกว่างานนั้นทำเงินได้เท่าไหร่ เพื่อให้รู้ว่าควร relay อะไรต่อ**

**เพดานที่ห้ามข้าม:** รายได้อยู่ได้ในฐานะเหตุผลให้ทำงานชิ้นถัดไปเท่านั้น
ห้ามโตเป็นหน้า analytics เอกเทศ ไม่มีกราฟ funnel cohort หรือ retention
ทุกตัวเลข ฿ ต้องมีทางกดไปสร้างงานต่อได้

## 3. Phase 0 — งานฐานที่ต้องทำก่อนฟีเจอร์ทุกตัว

> **สถานะ: เสร็จแล้ว** (commit ถัดจากเอกสารนี้) — `ContentStore` เป็น source of truth
> ตัวเดียว, seed คำนวณวันเวลาสัมพันธ์กับตอนนี้, กดเผยแพร่แล้วงานเข้ารายการจริง,
> Home / Content / Notifications อ่านชุดเดียวกัน, `demoContentJobs` ที่เป็น
> top-level list ถูกลบแล้ว, มี `reschedule` / `cancel` / `restore` / `retry` /
> `byProduct` พร้อมเทส 9 เคส

### ปัญหาที่มีอยู่วันนี้

"งาน" กระจายอยู่ 3 ที่ และไม่ตรงกัน

| แหล่ง | ใครอ่าน |
|---|---|
| `homeProvider` (ข้อมูลจาก backend) | หน้าหลัก |
| `demoContentJobs` (fixture คงที่) | หน้าคอนเทนต์ หน้าแจ้งเตือน |
| local state ในหน้า publish | ไม่มีใครอ่านต่อ |

ข้อบกพร่องที่ยืนยันแล้ว

1. **กดเผยแพร่แล้วงานหายไป** — `_submit()` ที่
   [publish_review_page.dart:277](../mobile/lib/features/create/presentation/publish_review_page.dart#L277)
   ตั้งแค่ `submitted = true` ไม่เขียนลงที่ใดเลย งานที่เพิ่งส่งไม่โผล่ในแท็บคอนเทนต์
2. **หน้าหลักกับหน้าคอนเทนต์แสดงคนละชุด** —
   [content_library_page.dart:38](../mobile/lib/features/home/presentation/content_library_page.dart#L38)
   เลือกแบบ either/or ไม่ใช่รวมกัน backend ว่างเมื่อไหร่ หน้าหลักขึ้น
   "ยังไม่มีคอนเทนต์" แต่หน้าคอนเทนต์โชว์ 5 งาน
3. **fixture ตรึงวันที่ไว้** —
   [content_detail_page.dart:8](../mobile/lib/features/home/presentation/content_detail_page.dart#L8)
   ใช้ `DateTime(2026, 9, 8, ...)` ทั้งชุด พ้นวันนี้ไปเดโมจะเพี้ยน
   และ Smart Planner จะแสดงสัปดาห์ว่างเปล่า
4. **หน้าหลักไม่โหลดซ้ำ** — หลังเปลี่ยนเป็น `StatefulShellRoute.indexedStack`
   หน้าหลักถูกสร้างครั้งเดียวและอยู่ยาว `load()` ใน `initState` ไม่ยิงอีก
   เหลือแค่ pull-to-refresh

### ทำไมต้องทำก่อน

ฟีเจอร์ที่วางแผนไว้ **แปดในสิบสองตัวอ่านหรือเขียน "งาน"**
ถ้าไม่มีแหล่งเดียว แต่ละตัวจะสร้าง fixture ของตัวเอง แล้วจะไม่ตรงกัน
เช่น Creator Pulse บอกว่ามีช่องว่าง 2 ช่อง แต่ Planner แสดงคนละชุด
หรือลากงานใน Planner แล้ว Pulse ไม่อัปเดต เดโมจะพังตรงจุดที่ตั้งใจให้ประทับใจที่สุด

### สิ่งที่ต้องส่งมอบ

`ContentStore extends ChangeNotifier` ลงทะเบียนใน
[providers.dart](../mobile/lib/app/providers.dart) เป็น source of truth ตัวเดียว

```
ContentStore
  List<PublishJob> jobs          // แหล่งเดียวของทั้งแอป
  seed()                         // fixture คำนวณจาก DateTime.now() ไม่ hardcode
  add(PublishJob)                // publish page เรียกตอน submit
  reschedule(id, DateTime)       // Smart Planner
  cancel(id) / restore(id)       // content detail
  retry(id)                      // งานที่ล้มเหลว
  updateStatus(id, JobStatus)    // Publish Journey
  byProduct(productId)           // สินค้า ↔ คอนเทนต์
```

**เกณฑ์ว่าเสร็จ**

- `_submit` เพิ่มงานเข้า store จริง แล้วงานนั้นโผล่ในแท็บคอนเทนต์ทันที
- หน้าหลักและหน้าคอนเทนต์อ่านชุดเดียวกัน เลิก either/or
- fixture ทุกตัวคำนวณวันที่สัมพันธ์กับวันนี้ เปิดแอปวันไหนก็สมเหตุสมผล
- ลบ `demoContentJobs` ที่เป็น top-level list ออก ย้ายเป็น seed ของ store
- เทสครอบคลุม add / reschedule / cancel / restore

**ประเมิน:** 150–200 บรรทัด บวกการปรับที่เรียกใช้ ทำครั้งเดียว ฟีเจอร์ที่เหลือได้ใช้ฟรี

## 4. ลำดับงาน

ลำดับนี้เรียงตาม **สายพึ่งพา** ไม่ใช่ความเด่นบนหน้าจอ

เหตุผลที่ Creator Pulse ไม่ได้อยู่อันดับแรกทั้งที่เด่นที่สุด: มันเป็น *ตัวสรุป*
ของสิ่งที่ยังไม่มี ทำก่อนแปลว่าต้องเขียนของปลอมไว้ แล้วรื้อทุกครั้งที่
ฟีเจอร์ต้นทางเสร็จ รวมแล้วรื้อ 3–4 รอบ ทำทีหลังเขียนรอบเดียวจบ

| ลำดับ | ฟีเจอร์ | พึ่ง | เหตุผลของตำแหน่ง |
|---:|---|---|---|
| 0 | **ContentStore** | — | ฐานของทุกอย่าง |
| 1 | **Content Readiness Score** | — | ไม่พึ่งใครเลย ได้ผลลัพธ์เด่นสุดต่อแรงที่ลง |
| 2 | **สินค้า ↔ คอนเทนต์** | 0 | join ของที่มีอยู่แล้ว ถูกที่สุดในรายการ |
| 3 | **Opportunity Radar** | 2 | ใช้ประวัติจากข้อ 2 มาแนะนำได้แม่นขึ้น |
| 4 | **Remix งานเก่า** | 0 | ต้องมีงานเก่าจริงให้รีมิกซ์ |
| 5 | **Batch mode** | 0, 4 | ใช้ flow เดิมวิ่ง N รอบ |
| 6 | **Smart Content Planner** | 0, 5 | ต้องมีงานจริงให้ลาก Batch เป็นตัวป้อนของ |
| 7 | **Swipe Review Queue** | 0 + lifecycle ใหม่ | ต้องเติม `JobStatus.awaitingReview` ก่อน |
| 8 | **รายได้ (แกนของ Recap)** | 0, 2 | ต้องแก้ brief ตามส่วนที่ 2 ก่อน |
| 9 | **Creator Pulse** | 1–8 | สรุปจากของที่มีจริงแล้ว เขียนรอบเดียวจบ |
| 10 | **Publish Journey** | 0 | ต่อยอด `updateStatus` |
| 11 | **Weekly Creator Recap** | 8, 9 | ปิดท้ายด้วยสรุปรายสัปดาห์ |

**ก้อนแรกที่แนะนำให้ทำรวดเดียว:** Phase 0 + Readiness Score
ปิดรูที่มีอยู่ และได้ฟีเจอร์เด่นตัวแรกในรอบเดียว

## 5. รายละเอียดต่อฟีเจอร์

### 1. Content Readiness Score — เสร็จแล้ว

`ReadinessReport.evaluate` (ฟังก์ชันล้วน) ให้คะแนน 6 หัวข้อรวม 100:
Hook / พูดถึงสินค้า / ชวนกดตะกร้า / ความยาวคลิป / รายละเอียดคำบรรยาย /
ความเสี่ยงคำกล่าวอ้าง — คิดจาก caption, แท็ก, durationSec, สถานะตะกร้า, สินค้า
การ์ดคะแนนอยู่เหนือ checklist ในหน้า publish, หัวข้อที่ยังไม่เต็มกดแล้วเลื่อน
ไปช่อง caption หรือ toggle ตะกร้า, คะแนนต่ำมาก (poor) ถามยืนยันครั้งเดียว
แล้วยังเผยแพร่ได้ — เตือน ไม่บล็อก ตามที่ตกลง เทส 8 เคส

ให้คะแนนก่อนเผยแพร่ กดหัวข้อที่คะแนนต่ำแล้วกระโดดไปแก้ตรงจุดได้

- **ตรวจอะไร:** Hook, การเห็นสินค้า, CTA ตะกร้า, ความยาว, caption, ความเสี่ยงด้านคำกล่าวอ้าง
- **mock ได้ทันที:** คำนวณจากข้อมูลที่ไหลเข้าหน้า publish อยู่แล้ว
  (`caption`, `durationSec`, `product`, `sourceLabel`) ไม่ต้องรอ store
- **ท่าที:** เตือนแต่ไม่บล็อก และเก็บว่าผู้ใช้ข้ามไป
  การบล็อกครีเอเตอร์ที่รู้ว่าตัวเองทำอะไรอยู่คือทางที่ทำให้คนเลิกใช้
- **เสร็จเมื่อ:** แต่ละหัวข้อกดแล้วพาไปยัง field ที่เกี่ยวข้องในหน้าเดียวกันได้

### 2. สินค้า ↔ คอนเทนต์ — เสร็จแล้ว

หน้า product detail มีการ์ด "คลิปของสินค้านี้": จำนวนคลิป, รายได้รวมโดยประมาณ
(`mockOrdersFor(job) × commissionBaht` ของคลิปที่โพสต์แล้ว), รายการคลิปกดเข้า
หน้า content detail ได้, ว่างเปล่าชวนเริ่มชิ้นแรก — อ่านจาก `ContentStore.byProduct`
เทส 2 เคส

ในหน้า product detail เพิ่มส่วนเดียว

```
คุณทำคลิปให้สินค้านี้ไปแล้ว 3 คลิป · ฿2,140
[รายการคลิป กดเข้าไปดูได้]
```

- **mock ได้ทันที:** `store.byProduct(id)` บวก `commissionBaht × ออเดอร์`
- **ได้อะไร:** เกิด loop การท่องแอป สินค้า → คลิป → รีมิกซ์ → สินค้า
- **ต้นทุน:** ต่ำที่สุดในรายการทั้งหมด ไม่มี concept ใหม่เลย

### 3. Opportunity Radar — เสร็จแล้ว

`Opportunity.scan` จัดอันดับสินค้า: เคยทำเงินได้ (proven) > ใกล้หมดสต็อก >
คอมสูงยังไม่มีคลิป > ยังไม่มีคลิป — หนึ่งใบต่อสินค้า สินค้าหมดสต็อกไม่ขึ้น
แถบ "โอกาสวันนี้" เป็น horizontal strip บนหน้า Showcase (ไม่มีหน้าของตัวเอง)
ทุกใบมีปุ่มสร้างคอนเทนต์ กดการ์ดเข้า product detail เทส 5 เคส

ในแท็บ Showcase แจ้งสินค้าที่ควรสนใจ

- คอมมิชชันเพิ่ม / ใกล้หมดสต็อก / ยังไม่มีคอนเทนต์ / เคยทำแล้วได้ผลดี
- **ข้อสุดท้ายสำคัญที่สุด** เพราะอิงจากสิ่งที่ผู้ใช้คนนี้ทำแล้วเวิร์ค
  ไม่ใช่ข้อมูลทั่วไป — ต้องมีข้อ 2 ก่อนถึงทำได้
- **ห้าม:** ให้มีหน้าของตัวเอง ต้องอยู่ในหน้า Showcase ที่มีอยู่

### 4. Remix งานเก่า — เสร็จแล้ว

หน้า content detail → เมนู → "ทำเวอร์ชันใหม่" → เลือก 5 แบบ
(เปลี่ยน Hook / เปลี่ยนคำชวนกดตะกร้า / เวอร์ชัน 15 วินาที / เปลี่ยนสินค้า /
เขียนคำบรรยายใหม่) → เปิดหน้า publish พร้อมแบนเนอร์บอกว่าให้แก้อะไร +
seed caption/duration ที่เหมาะกับแต่ละแบบ RelayContent ไม่เขียน hook/สคริปต์ให้
งานที่รีมิกซ์เข้า store พร้อม `remixOfId` ชี้งานต้นทาง เทส 5 เคส

จากหน้าคอนเทนต์ กด "ทำเวอร์ชันใหม่" แล้วเลือก

- เปลี่ยน Hook / เปลี่ยน CTA / ทำเวอร์ชัน 15 วินาที / เปลี่ยนสินค้า / caption ใหม่
- **หมายเหตุขอบเขต:** "เปลี่ยน Hook" ในที่นี้คือ *ส่งกลับไปทำใหม่พร้อมโจทย์ที่ต่างไป*
  ไม่ใช่ให้ RelayContent เขียน hook ให้ ดูเส้นแบ่งในส่วนที่ 1
- **เสร็จเมื่อ:** งานที่รีมิกซ์เข้า store เป็นงานใหม่ที่อ้างถึงงานต้นทางได้

### 5. Batch mode

- **ที่มา:** brief ระบุไว้เองว่าผู้ใช้ "ต้องผลิตหลายคลิปต่อสัปดาห์"
  แต่ทุกอย่างในแอปตอนนี้เป็น single-item
- เลือกสินค้า 3 ตัว → วิ่งผ่าน flow เดียวกันรวด → Planner กระจายลงสัปดาห์ให้
- **ได้อะไร:** ให้ "ของให้ทำ" เยอะสุดต่อแรงที่ลง และทำให้ Planner มีของให้ลากจริง

### 6. Smart Content Planner — เสร็จแล้ว

`ContentPlanner` — toggle มุมมอง list/ปฏิทิน ที่ AppBar ของแท็บคอนเทนต์
(เลือกทางเลือกที่ 1 ตามที่เอนเอียงไว้) 7 วันจันทร์–อาทิตย์ ของสัปดาห์ที่เลือก
เลื่อนสัปดาห์ได้ ลาก (long-press) งานข้ามวันเพื่อเปลี่ยนวันโพสต์ (คงเวลาเดิม)
เรียก `store.reschedule` วันว่างและวันที่ไม่มีงานตั้งเวลาโชว์เวลาที่แนะนำ
งานที่โพสต์แล้ว/ล้มเหลว ลากไม่ได้ เทส 2 เคส (render + drag)

### 7. Swipe Review Queue

### 8. รายได้

- **ของที่มีอยู่แล้วแต่ไม่เคยคูณกัน:**
  [content_detail_page.dart:494](../mobile/lib/features/home/presentation/content_detail_page.dart#L494)
  รู้ว่าคลิปนี้ได้ 38 ออเดอร์ และ
  [showcase_product.dart:28](../mobile/lib/features/showcase/domain/showcase_product.dart#L28)
  รู้ว่าคอม ฿240/ชิ้น แต่ทั้งแอปไม่มีตัวเลข ฿ ที่บอกว่าผู้ใช้ได้เงินเท่าไหร่
- **รูปแบบที่เสนอ**

  ```
  สัปดาห์นี้  ฿4,820   ↑ 38% จากสัปดาห์ก่อน
  คลิปที่ทำเงินสุด: "3 เหตุผล..."  ฿2,140 · 38 ออเดอร์
  เซรั่มทำเงินให้คุณ 3 สัปดาห์ติด → ทำคลิปที่ 4 ไหม
  ```

  บรรทัดสุดท้ายสำคัญที่สุด มันเปลี่ยนตัวเลขให้เป็นเหตุผลที่ต้องกลับมาสร้างอีก
- **ทดสอบขอบเขต:** ทุกตัวเลข ฿ ต้องมีปุ่มพาไปสร้างงานต่อ
  ถ้าตัวเลขไหนกดแล้วไม่พาไปไหน ตัวเลขนั้นไม่ควรอยู่ในแอปนี้

### 9. Creator Pulse

สรุปทุกเช้าว่าวันนี้ควรทำอะไร

- ดึงจากของจริงที่เสร็จแล้ว: ช่องว่างจาก Planner, งานที่ต้องแก้จาก Readiness,
  คลิปที่ควรรีมิกซ์จาก Remix, โอกาสจาก Radar, ตัวเลขจากรายได้
- **ที่อยู่:** บนสุดของหน้าหลัก แทน `_QuickRelayBar` ปัจจุบันหรืออยู่เหนือมัน

### 10. Publish Journey

เส้นทางสด เข้าคิว → เตรียมไฟล์ → ส่ง TikTok → กำลังตรวจ → เผยแพร่แล้ว

- **มีอยู่ใน brief แล้ว:** "บอกเสมอว่างานอยู่ขั้นไหน หากเกิดปัญหา
  แอปต้องอธิบายสิ่งที่เกิดขึ้น" — ไม่ใช่ของเสริม แต่เป็นของที่สั่งไว้แล้วยังทำไม่ครบ
- งานที่ผิดพลาดต้องแก้หรือ retry ได้จากจุดนั้นทันที

### 11. Weekly Creator Recap

- **เปลี่ยนแกนจาก activity เป็น money** — เดิมวางไว้ว่า "สร้างกี่คลิป
  ใช้สินค้าอะไรบ่อย" ซึ่งเป็น log กิจกรรม ไม่ใช่ผลลัพธ์
- ปิดท้ายด้วยข้อเสนอ 3 งานถัดไปที่กดทำต่อได้ทันที

### ตัดออก — โครงคลิปของฉัน

เดิมเสนอให้เซฟ Hook + โครง + แพตเทิร์น caption + แฮชแท็กเป็นเทมเพลต

**ตัดออกเพราะเสี่ยงข้ามเส้นในส่วนที่ 1** ถ้าจะทำภายหลัง ให้เก็บได้เฉพาะ
ฝั่งซ้ายของตารางเส้นแบ่ง (caption, แฮชแท็ก, ตำแหน่งตะกร้า, ความยาวเป้าหมาย)
ห้ามแตะสคริปต์หรือ hook เด็ดขาด — ถ้าข้ามไปฝั่งขวา RelayContent จะไปแข่งกับ
Google Flow และ Sora ซึ่งเราแพ้แน่นอน

## 8. หมายเหตุเรื่องตัวเลขความคืบหน้า

`ui-implementation-status.md` ปัจจุบันประกาศ 100% ทั้ง 12 แถว
ตัวเลขนั้นถูกต้องในความหมาย **"หน้าจอครบตาม prototype ที่กำหนดไว้"**
แต่ไม่ได้แปลว่าผลิตภัณฑ์มีความน่าสนใจครบแล้ว

เสนอให้เอกสารนั้นเปลี่ยนชื่อ metric ให้ตรง เช่น
**Prototype scope coverage: 100%** และเพิ่มคอลัมน์ที่สอง
**Known prototype limitation** สั้น ๆ ต่อแถว จะได้ทั้งการประกาศความสำเร็จ
และแผนงานในตารางเดียว โดยไม่เสียส่วนที่เคยใช้วางแผนได้ไป
